# Skill Configuration Pattern

Skills that adapt to a project use the **configure/learn** lifecycle to generate and maintain a config file. This document defines the pattern, its rules, and how to validate skills against it.

See [INSTALLATION-MODELS.md](./INSTALLATION-MODELS.md) for where config files are saved depending on installation model.

## Overview

```
/skill configure    →  Discover from project structure/configs  →  Propose to user  →  Save config
/skill learn        →  Analyze actual code/history              →  Propose updates   →  Update config
/skill              →  Read config (or use defaults)            →  Execute procedure
```

## Commands

### configure

First-time setup. Scans project structure and existing configuration files to discover settings.

**Must**:
1. Scan relevant project sources (directory structure, config files, docs)
2. Propose discovered configuration to user — never save without confirmation
3. Save config to the correct path based on installation model (see INSTALLATION-MODELS.md)
4. Be idempotent — running again overwrites with fresh discovery

**Sources vary by skill**:

| Skill | Discovery Sources |
|-------|-------------------|
| commit | Directory structure, commit history, package workspaces |
| arch | CLAUDE.md, README, tsconfig/eslint/go.mod, directory structure |
| code | Linter/formatter configs (.eslintrc, .prettierrc, pyproject.toml, etc.) |
| debugger | Log commands, env vars, service names, deployment targets |
| deploy | CI/CD configs, npm scripts, Taskfile tasks |
| domain-expert | Documentation, glossaries, ADRs |
| pr-create | PR template location |
| pr-merge | Merge strategy preferences |

### learn

Update existing config by analyzing actual code and history, not just static configuration. Not all skills support learn — only skills where runtime analysis adds value beyond what configure discovers.

**Must**:
1. Read existing config first
2. Analyze actual code, logs, or history (not just config files — that's configure's job)
3. Propose updates to user — never save without confirmation
4. Merge into existing config, not replace entirely

**Skills with learn**:

| Skill | What learn Analyzes |
|-------|---------------------|
| commit | Recent commit history for new scope patterns |
| arch | Import patterns to infer actual architecture vs documented |
| code | Representative source files for naming/formatting conventions |
| debugger | Service logs and error patterns |
| deploy | Recent deployment history |
| domain-expert | Domain code (entities, value objects, relationships) |

**Skills without learn** (configure is sufficient):

| Skill | Why |
|-------|-----|
| pr-create | Template is static — no runtime patterns to learn |
| pr-merge | Strategy is a preference — no patterns to learn from code |

## Config File

### Location

Determined by installation model (see [INSTALLATION-MODELS.md](./INSTALLATION-MODELS.md)):

- **Standalone**: `.claude/skills/<skill-name>.yaml`
- **my-workflow**: `.claude/skills/<skill-name>/<skill-name>.yaml`

### Schema

Every config file must include:

```yaml
version: 1
discovered_at: "ISO-8601 timestamp"

# Skill-specific configuration below
```

- `version` — schema version, for future migration
- `discovered_at` — when configure/learn last ran

### Documenting in skill.yaml

Use `config_refs` with comments pointing to both config paths:

```yaml
# Optional project configuration generated by /<skill-name> configure
# Config location depends on installation model:
#   Standalone installation: .claude/skills/<skill-name>.yaml
#   my-workflow installation: .claude/skills/<skill-name>/<skill-name>.yaml
config_refs:
  - <key>              # Optional: description
```

### Documenting in SKILL.md

Include a **Save Location** section under the configure command, and a **Reads config from** section under normal usage. Both must list the precedence order:

1. `.claude/skills/<skill-name>/<skill-name>.yaml` (my-workflow)
2. `.claude/skills/<skill-name>.yaml` (standalone)
3. Skill defaults

## Validation Checklist

Use this when reviewing or updating a skill that has configuration:

### Structure

- [ ] `skill.yaml` has `config_refs` with both installation paths in comments
- [ ] `SKILL.md` has a **Save Location** section with the installation model table
- [ ] `SKILL.md` has a **Reads config from** section with precedence order
- [ ] Config schema is documented in SKILL.md with example YAML

### configure command

- [ ] Discovers from project sources (not hardcoded values)
- [ ] Proposes config to user before saving
- [ ] Saves to correct path based on installation model
- [ ] Idempotent — safe to re-run

### learn command (if supported)

- [ ] Reads existing config first
- [ ] Analyzes runtime artifacts (code, history, logs) — not just static config
- [ ] Proposes updates before saving
- [ ] Merges into existing config, does not replace

### Normal usage

- [ ] Reads config using precedence order
- [ ] Works with defaults when no config exists
- [ ] Does not require configure to have been run first

## Skills Without Configuration

Not all skills need configuration. Skills that operate the same regardless of project context (e.g., pure procedure-following skills) should not have configure/learn commands or config_refs.
